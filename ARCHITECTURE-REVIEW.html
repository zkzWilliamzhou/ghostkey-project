Implemented candidate

Strong · implemented

Put the four responsibilities behind real seams

Files
ghostkey/core.py → model.py, keys.py, walk.py, surfaces.py, analyze.py, render.py, scan.py
Problem
Every reader of core.py had to hold the filesystem trust boundary, seven surface parsers, the key join and three serializers in one head. A change to TOML parsing sat next to SARIF output. Locality was zero. Tests reached past the interface into private helpers because nothing else existed.
Solution
Move each responsibility verbatim into its own module with an ast-based splitter. core.py becomes a facade that re-exports the frozen names. scan.run(options) is the composition root. Callers and tests still cross the same seam.
Benefits
Locality: a YAML fix now lands in surfaces.py alone. Leverage: one render(result, options) interface serves three adapters (text, JSON, SARIF), so two adapters make the renderer seam real. Depth: each module hides a large implementation behind two or three functions.

Deletion test. Delete surfaces.py and parsing complexity does not vanish; it reappears across every caller. The module earns its keep. Delete core.py's facade and only re-exports vanish, which is why it stays thin on purpose.

Candidates not built

Speculative · not implemented

Replace the surface if/elif chain with an adapter registry

A SurfaceAdapter interface with one method per parser would let a contributor add a language without touching _extract. Today there is one parser chain and one consumer, so the seam would have exactly one adapter. Per the codebase-design vocabulary, one adapter means a hypothetical seam. Adding it now would be YAGNI. Revisit when a second extraction path exists.

Why it is listed. This is the obvious next deepening, but it is not work we did. The refactor moved _extract verbatim into surfaces.py; claiming a registry was built would be false.
Speculative · not implemented

Swap regex source matching for a compiled DFA

Twelve compiled linear patterns over bounded lines are cheap and have no nested quantifiers. A DFA would add a large implementation behind an interface that already has depth. No measured bottleneck justifies it.

Top recommendation

The implemented split comes first because it removed the only real friction: a reader could not find the code that owned a decision. It also created the seam that makes the other two candidates possible later. Neither speculative candidate changes the report schema, so both remain open without blocking a release.

Behavior freeze

scripts/deepen.py reads the v1 source, extracts every top-level node with ast, and writes each function body verbatim into its owning module. core.py then re-exports the same names. Six frozen cases cover exit code, stdout bytes, stdout length and stderr. A mutation test proves the oracle detects a changed key.
